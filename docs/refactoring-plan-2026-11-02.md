## 2. 競合他社の視点から見た問題点（3 つ）と解決策（1 つ）

1. **機能を出す速さで負け始めている。** 画面の操作を 1 つ足すたびに、シェル → ホーム／一覧／検索 → `CardList` と、同じ callback を 2〜4 か所に通している。Eight・Sansan はサーバー側の 1 つの操作 API から全画面を作るので、足すのは 1 か所で済む。
2. **品質を保証する厚みで負ける。** 利用者が一番触る 2 つのクラス（シェルと確認画面）に自動テストがない。そのため、この 2 か所の不具合はレビュー担当の目視でしか見つからない。競合は QA チームと段階的な配信を持つ。
3. **規模で負ける。** 営業職は名刺が数千枚になる。当アプリは、タブを移るたびと保存のたびに全件をディスクから読み直す。枚数に比例して遅くなる作りで、実機での上限を測っていない。

**解決策（1 つ）: 画面とデータの間に「アプリケーション層」を 1 つ置く。**
- `CardRepository`: `CardStore` の上に、メモリ上の一覧キャッシュを持つ。書き込みのたびに差分だけ更新し、一覧ファイルの書き直しはまとめて 1 回にする。
- `CardActions`: 削除・元に戻す・まとめる・連絡済み・自分の名刺・共有・復元を、**ダイアログを出さない純粋な Dart の操作**として切り出す。結果は値で返し、ダイアログとトーストは画面が出す。電話帳・共有・ファイル選択はインターフェース（ポート）越しに呼ぶので、テストでは偽物に差し替えられる。
- 画面には `CardActions` を 1 つ渡す。`CardList` の callback 7 個は、この 1 つの引数にまとまる。

## 3. 利用者の視点で不便なこと（3 つ）と解決策（1 つ）

1. **電話帳から取り込んだ住所やメモの 2 行目以降が消える**（上の実測）。ビル名や部屋番号が一覧・CSV・Obsidian に出ない。
2. **アプリが落ちたり電池が切れたりすると、設定や名刺が壊れることがある。** 設定ファイルが壊れると、登録先・自分の名刺・外部保存日が黙って初期化される。
3. **「まとめる」を後から戻すと、半分しか戻らない。** 8 秒を過ぎた後にゴミ箱から戻せるのは古い名刺だけで、新しい名刺はまとめた後の内容のまま残る。

**解決策（1 つ）: 保存の安全装置を `CardStore` の 1 か所に集める。**
- 値の正規化: frontmatter に書く値の改行は ` / ` に置き換える。JSON は元の値のまま。
- 原子的な書き込み: 一時ファイルに書いてから `rename` する。golden JSON・settings.json・jobs.json・learned.json が対象。
- 上書き前の版を残す: まとめる・電話帳からの取り直し・復元で上書きされる名刺は、上書き前の JSON を `trash/<stem>/versions/` に残す（7 日）。「削除した名刺を戻す」と同じ画面から戻せるようにする。

## 5. やらないこと（理由と、やるときの条件）

- **状態管理ライブラリ（Riverpod、Bloc など）の導入**: 新しい依存と学習コストがかかる。`CardActions` と `ValueNotifier` で足りる。画面をまたぐ状態が今の 3 倍になったら考える。
- **データベース（SQLite、Isar）への移行**: Obsidian で読めるノートと golden JSON が、この製品の価値そのもの。キャッシュで速さが足りなくなったら、索引だけ DB にする。
- **文言の一元管理（多言語化）**: 利用者は日本語だけ。英語版を出すと決めたときに行う。
- **ScanPage を最初から全面的に書き直すこと**: R6 は依存の注入とテストの追加だけにする。分割はテストができてから、1 メソッドずつ行う。
