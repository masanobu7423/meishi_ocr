# 名刺スキャン 総合評価と S+ への計画（2026-11-02）

対象: HEAD 3cdecc5（テスト 298 件、全通過、CI 成功）。製品版は v0.2.9 (12)、内部テストは v0.2.14 (17)。
評価は忖度なしで付ける。根拠は、計測した数字・テスト・実機での確認の 3 つだけにする。実機で確かめていない機能は、コードとテストが揃っていても A を上限にする。

## 1. 評価の尺度

| 評価 | 意味 |
|---|---|
| S+ | 競合（Eight・Sansan・CamCard）と並ぶか上回る。自動テストと実機の両方で裏付けがある |
| S | 競合と並ぶ。裏付けはあるが、1 つ弱いところがある |
| A | 作りとテストは揃っている。実機の確認か規模の検証が足りない |
| B | 動くが、既知の欠陥か大きな未検証がある |
| C | 利用者や公開に実害が出得る欠陥がある |

2. 既知のデータ不具合（改行）と、原子的でない書き込み。
3. 実機で確かめていない機能が多い。
4. 構造の肥大（テストのない 2 クラス）。

## 3. 競合他社の視点から見た問題点（3 つ）と解決策（1 つ）

1. **信頼の土台で負ける。** Eight・Sansan は法人の監査に耐えるプライバシーポリシーとセキュリティの説明を持つ。当アプリのポリシーは実際の動作より狭く書かれていて、それ自体が規約上のリスクになっている。
2. **出荷の確かさで負ける。** 競合は段階的な配信とクラッシュの監視で、変更を小さく出す。当アプリは、確かめていない 9 回分の変更を一度に製品版へ出そうとしている。
3. **精度の主張に根拠が足りない。** 競合は精度を数字で示す（手入力による保証）。当アプリの数字は 28 枚の標本で、建設業の項目は各 1 枚しかない。

**解決策（1 つ）: 「出荷の門」を決め、通ったものだけを製品版にする。** 門は次の 5 つ。
- ① ポリシーが実際の動作と一致していること
- ② 既知のデータ不具合が 0 件であること
- ③ 実機の確認表がすべて埋まっていること
- ④ golden が 60 枚以上あり、氏名・会社・住所が 95% 以上であること
- ⑤ 段階的な配信（20% → 100%）と、Android vitals の確認

## 4. 利用者の視点で不便なこと（3 つ）と解決策（1 つ）

1. **新しい機能が製品版に届かない。** 台帳・接点・要確認・まとめる・ゴミ箱は、製品版の利用者にはまだ見えない。
2. **機能が増えて、どこに何があるか分からない。** 使い方の案内がアプリ内にもストアにもない。メニューのシートには説明を付けたが、全体像は分からない。
3. **電話帳から取り込んだ住所が欠ける**（既知の不具合）。

**解決策（1 つ）: 「直してから、小さく、説明付きで届ける」。**
- 不具合（R0）とポリシーを直した版を、製品版 v0.3.0 として段階配信する。
- ストアの説明文とスクリーンショットを、台帳・連絡予定・要確認の 3 つを軸に作り直す。
- アプリの初回起動とアップデート後に「新しくできること」を 1 枚だけ出す（閉じたら二度と出ない）。

- E7 は E1〜E3 が通ってから。

## 6. 実機の確認表（E3 で埋める）

| 機能 | 手順 | 期待する結果 |

| CSV | 共有して Excel で開く | 文字化けせず、列見出しが日本語で出る |

## 7. 測り方（評価を毎回同じ物差しで付け直すため）

- 精度: `flutter test test/golden_test.dart` の表。標本の枚数と内訳（実物・合成・縦書き）を並べて記録する。
- 規模: P08_T で合成の 2,000 枚を使い、タブ移動・保存・起動の時間を測る。
- 品質: テスト件数、2 つの大きいクラスの行数、CI の結果、既知の不具合の件数（README の「既知の不具合」節に置く）。
- 運用: 製品版との差（何回分の変更が未出荷か）、vitals のクラッシュ率と ANR 率。
- 規約: ポリシーと機能の対応表の空欄の数（目標は 0）。

この評価は、E1〜E8 のどれかが完了するたびに付け直す。日付を付けた新しい版を `docs/evaluation-<日付>.md` に置く。
